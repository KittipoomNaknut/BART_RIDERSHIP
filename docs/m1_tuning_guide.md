# M1: การจูนโมเดล ปรับอะไรบ้าง และปรับเพื่ออะไร

เอกสารนี้อธิบายว่าตอนจูน M1 (พยากรณ์ entries รายสถานี-ชั่วโมงล่วงหน้า 7 วัน) เราปรับค่าอะไรบ้าง แต่ละค่าทำหน้าที่อะไร และทำไมถึงลองในช่วงนั้น
ผลของการจูนอยู่ในอีกไฟล์ `docs/m1_tuning_results.md`

โค้ดอยู่ใน `notebooks/08_m1_forecast.ipynb` หัวข้อ 6 (ทดลอง 10 trial) และหัวข้อ 7 (จูนเต็ม 50 trial)

## 1. จูนคืออะไร

XGBoost สร้างต้นไม้ตัดสินใจทีละต้น ต้นใหม่จะพยายามแก้ error ของต้นก่อนหน้า
ก่อนเทรนต้องตั้ง "ปุ่มปรับ" (hyperparameter) หลายตัว เช่น ต้นไม้ลึกกี่ชั้น หรือเรียนรู้เร็วแค่ไหน
ค่าที่ดีที่สุดขึ้นกับข้อมูลแต่ละชุด จึงต้องลองหลายชุดแล้วเลือกชุดที่พยากรณ์แม่นที่สุด

---

## 2. ค่าที่ปรับและหน้าที่ของแต่ละตัว

### 2.1 ขนาดและความซับซ้อนของต้นไม้

**max_depth** ช่วงที่ลอง 6-12
- จำนวนชั้นสูงสุดของต้นไม้แต่ละต้น
- ยิ่งลึกยิ่งจับความสัมพันธ์ที่ซับซ้อนได้ เช่น "สถานี EMBR + ชั่วโมง 17 + วันอังคาร + หลังวันหยุด" พร้อมกัน
- ถ้าลึกเกินไปจะเริ่มจำข้อมูล train (overfit) และเทรนช้าลงมาก
- ข้อมูลเรามี 50 สถานี × 24 ชั่วโมง × 7 วัน × วันหยุด จึงต้องการต้นไม้ค่อนข้างลึก ช่วงจึงเริ่มที่ 6

**min_child_weight** ช่วงที่ลอง 1-50 (สุ่มแบบ log)
- ใบไม้หนึ่งใบต้องมีข้อมูลมากพอ (วัดเป็นผลรวม hessian ของแถวในใบนั้น) ถึงจะแตกกิ่งต่อได้
- ค่าสูงกันไม่ให้โมเดลสร้างกฎจากกลุ่มเล็กๆ ที่บังเอิญ เช่น ชั่วโมงตี 3 ของสถานีเล็ก
- ใช้คู่กับ max_depth ต้นไม้ลึกได้ แต่ทุกใบต้องมีข้อมูลรองรับ

### 2.2 ความเร็วในการเรียนรู้

**learning_rate** ช่วงที่ลอง 0.02-0.15 (สุ่มแบบ log)
- ต้นไม้แต่ละต้นแก้ error ได้มากแค่ไหน
- ค่าต่ำต้องใช้ต้นไม้มากขึ้น แต่มักแม่นกว่า เพราะแต่ละต้นแก้ทีละน้อย ไม่แก้เกิน
- ค่าสูงเทรนเร็ว แต่อาจพลาดจุดที่ดีที่สุด
- จำนวนต้นไม้ไม่ได้จูนตรงๆ ใช้ early stopping หาให้ (ดูข้อ 3)

### 2.3 ความสุ่ม (ลด overfit)

**subsample** ช่วงที่ลอง 0.6-1.0
- แต่ละต้นไม้สุ่มใช้แถวข้อมูลแค่บางส่วน เช่น 0.8 คือใช้ 80% ของแถว
- ต้นไม้แต่ละต้นจึงต่างกันเล็กน้อย พอรวมกันแล้วไม่ยึดติดกับแถวใดแถวหนึ่ง

**colsample_bytree** ช่วงที่ลอง 0.5-1.0
- แต่ละต้นไม้สุ่มใช้ feature แค่บางส่วน
- เรามี lag หลายตัวที่คล้ายกัน (lag_1w, lag_4w_mean, lag_4w_median) ถ้าไม่สุ่ม โมเดลอาจพึ่ง feature ตัวเดียวมากเกินไป

### 2.4 ค่าปรับโทษ (regularization)

**lambda** ช่วงที่ลอง 0.1-20 (สุ่มแบบ log)
- ปรับโทษ L2 กับค่าที่ใบไม้ให้ออกมา ทำให้ค่าในใบไม่สุดโต่ง
- ช่วยกับข้อมูลที่มีค่าผิดปกติ เช่น วัน Pride หรือขบวนพาเหรด

**alpha** ช่วงที่ลอง 0.01-5 (สุ่มแบบ log)
- ปรับโทษ L1 ทำให้ใบที่ไม่ค่อยมีประโยชน์มีค่าเป็น 0
- ทำให้โมเดลเรียบง่ายขึ้น

### 2.5 รูปแบบของ error (เฉพาะงานนับจำนวน)

**tweedie_variance_power** ช่วงที่ลอง 1.1-1.9
- objective ของเราคือ Tweedie เหมาะกับข้อมูลนับที่มีศูนย์เยอะและ variance โตตาม mean
- ค่านี้บอกว่า variance โตเร็วแค่ไหนเมื่อ mean เพิ่ม (1 = Poisson, 2 = Gamma)
- EDA ส่วนที่ 1.4 ประมาณไว้ ~1.4 จึงให้ค้นหารอบๆ ค่านั้นทั้งช่วง 1.1-1.9

### 2.6 ข้อมูลที่ใช้เทรน (ไม่ใช่ hyperparameter ของ XGBoost แต่จูนไปพร้อมกัน)

**variant** ตัวเลือก all / weighted / post_covid
- all: ใช้ข้อมูลทั้งหมดตั้งแต่ปี 2011
- weighted: ใช้ทั้งหมด แต่ข้อมูลเก่ามีน้ำหนักน้อยลง
- post_covid: ใช้แค่ มิ.ย. 2020 ถึง มิ.ย. 2022
- คำถามธุรกิจคือ ข้อมูลก่อน COVID ซึ่งระดับต่างจากตอนนี้มาก ยังช่วยหรือทำให้แย่ลง ให้ผลบน valid เป็นตัวตัดสิน

**half_life_years** ช่วงที่ลอง 0.5-4 ปี (ใช้เมื่อเลือก weighted)
- ข้อมูลเก่ามีน้ำหนักลดลงครึ่งหนึ่งทุกกี่ปี นับจาก 2022-07-01
- เช่น 2 ปี: ข้อมูลปี 2020 มีน้ำหนักครึ่งหนึ่ง ปี 2018 หนึ่งในสี่

## 3. ค่าที่ไม่ได้จูน (ตั้งไว้คงที่)

| ค่า | ตั้งไว้ | เหตุผล |
|---|---|---|
| objective | reg:tweedie | ข้อมูลนับ มีศูนย์ และ overdispersion (EDA 1.4) |
| tree_method / device | hist / cuda | เทรนบน RTX 4060 |
| max_bin | 256 | จำนวนช่วงที่แบ่งค่าแต่ละ feature ใน QuantileDMatrix |
| จำนวนต้นไม้ | สูงสุด 3,000 | หยุดเองด้วย early stopping |
| early stopping | 100 รอบ | ถ้า error บน valid ไม่ดีขึ้น 100 ต้นติด ให้หยุด และใช้จำนวนต้นที่ดีที่สุด |
| eval_metric | mae | ใช้ทำ early stopping เรียงลำดับโมเดลเหมือน WAPE บนข้อมูลชุดเดียวกัน |
| seed | 42 | รันซ้ำได้ผลเดิม |

## 4. วิธีวัดว่าชุดไหนดีกว่า

- เทรนบน **train** (2011-01 ถึง 2022-06 ไม่รวมช่วง break 2020-03-09 ถึง 2020-05-31)
- วัดบน **valid** (2022-07 ถึง 2022-12) ด้วย **WAPE** = ผลรวม |จริง - พยากรณ์| / ผลรวมค่าจริง ยิ่งต่ำยิ่งดี
- **ไม่แตะ test** (2023-01 ถึง 2023-05-02) ระหว่างจูน ใช้ครั้งเดียวตอนจบ
- ค่า valid ของ trial ที่ดีที่สุดจะดีเกินจริงเล็กน้อย เพราะใช้ข้อมูลชุดนี้เลือกด้วย ตัวเลขที่รายงานจริงคือค่า test

## 5. Optuna เลือกชุดถัดไปอย่างไร

ใช้ sampler แบบ TPE (Tree-structured Parzen Estimator)
1. trial ช่วงแรกลองกระจายทั่วช่วง เพื่อสำรวจ
2. จากนั้นแบ่ง trial ที่ผ่านมาเป็นกลุ่มที่ได้ผลดีกับกลุ่มที่ได้ผลแย่
3. เลือกชุดใหม่ที่หน้าตาคล้ายกลุ่มดีมากกว่ากลุ่มแย่
4. ทำซ้ำ ผลจึงค่อยๆ ดีขึ้นและนิ่ง

ข้อดีเมื่อเทียบกับ grid search: ไม่ต้องลองทุกชุด (ซึ่งมีเป็นล้านชุด) และค้นหาหลายค่าพร้อมกันได้

## 6. สิ่งที่ทำให้จูนเร็วและไม่ค้าง

- ข้อมูล train ~4.5 ล้านแถวอยู่บน GPU ในรูป QuantileDMatrix (แบ่งค่าเป็น bin ล่วงหน้า ใช้ VRAM น้อย)
- matrix ของแต่ละแบบข้อมูลสร้างครั้งเดียวแล้วใช้ซ้ำทุก trial
- ทุก trial บันทึกลง SQLite (`outputs/models/m1_optuna.db`) ทันทีที่เสร็จ ถ้าหยุดกลางคันผลไม่หาย รันต่อได้
- แต่ละ trial มีเพดาน 3,000 ต้นไม้ และทั้งรอบมีเพดานเวลา 60 นาที
- พิมพ์ความคืบหน้าทุก trial พร้อมเวลาที่น่าจะเหลือ

## 7. หลังจูนเสร็จ

1. เทรนชุดที่ดีที่สุดบน train อีกครั้ง 2 แบบ คือ learning rate ที่จูนได้ กับครึ่งหนึ่งของค่านั้น (เพดาน 6,000 ต้นไม้) แล้วเลือกแบบที่ WAPE บน valid ดีกว่า พร้อมได้จำนวนต้นไม้ที่เหมาะ
2. เทรนใหม่บน train + valid ด้วยจำนวนต้นไม้นั้น +5% ให้โมเดลเห็นข้อมูลล่าสุดก่อนพยากรณ์ปี 2023
3. โมเดล quantile (P10/P50/P90) ใช้ค่าชุดเดียวกัน แต่ต้นไม้ไม่เกิน 8 ชั้นและ learning rate 0.05 เพื่อให้เทรนเร็ว
4. วัดผลบน test ครั้งเดียว
