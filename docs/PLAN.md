## 2. ข้อมูล

| รายการ | รายละเอียด |
|---|---|
| แหล่งข้อมูล | BART Origin-Destination ridership — http://64.111.127.166/origin-destination/ |
| ไฟล์ | `data/raw/ridership/date-hour-soo-dest-YYYY.csv` จำนวน 13 ไฟล์ (2011–2023) |
| ขนาด | ~2.9 GB, 112,536,132 แถวใน CSV (ไม่นับ header) |
| หลังตัดแถวซ้ำ | **112,520,054 แถว, 1,194,454,788 ทริป** (ตัดแถวซ้ำ 16,078 แถว / 240,983 ทริป) |
| คอลัมน์ | `Date, Hour, Origin Station, Destination Station, Trip Count` |
| สถานี | 50 สถานี |

### ข้อควรระวังที่ตรวจพบแล้ว (ต้องจัดการใน notebook 02 และดูผลกระทบใน EDA)

1. **ไม่มีแถวที่ trip = 0** เพราะ feed ตัดทิ้งไว้ ถ้าจะทำ ML ต้องเติมศูนย์กลับ (zero-fill)
2. **feed ขาดไป 9 วัน**: 2011-10-15, 2011-11-05, 2012-11-03, 2013-10-19, 2013-10-20, 2020-01-21, 2020-02-19, 2020-02-24, 2020-04-28 วันพวกนี้ต้องเป็น "ไม่มีข้อมูล" ไม่ใช่ 0
3. **สถานีใหม่มีทริปหลงก่อนวันเปิดจริง** ต้องกำหนดวันเปิดจากข้อมูล (วันแรกที่มีผู้โดยสารเข้า ≥ 100 คน) แล้วตรวจกับวันเปิดทางการ:
   - WDUB 2011-02-19, OAKL 2014-11-22, WARM 2017-03-25
   - ANTC / PCTR 2018-05-26
   - MLPT / BERY 2020-06-13
4. **เดือน พ.ค. 2023 มีแค่ 2 วัน** ต้องตัดออกเวลาสรุปรายเดือน
5. **COVID shelter-in-place (2020-03-17)** เป็น structural break ต้องจัดการแยกทั้งในการวิเคราะห์และในโมเดล
6. **CSV มีแถวซ้ำข้ามไฟล์ 16,078 แถว**: ไฟล์ปี 2011–2017 มีข้อมูล hour 0–2 ของวันที่ 1 มกราคมของปีถัดไปติดมาด้วย ซึ่งไฟล์ปีถัดไปก็มีอยู่แล้ว ค่า trips ตรงกันทุกแถว ตัดด้วย DISTINCT แล้วใน notebook 01 (ถ้าไม่ตัด ยอดตี 0–2 ของวันปีใหม่จะเป็น 2 เท่า)
7. **มีทริปเข้าและออกสถานีเดียวกัน** 2,369,041 แถว / 6,527,179 ทริป (~0.5% ของทริป) ตัดสินใจแล้ว: นับรวมใน entries/exits ของสถานี เพราะผ่านประตูจริง (ไม่กระทบ Q3 เพราะไม่ข้ามฝั่งอ่าว)
8. **BART strike 2 ครั้งในปี 2013**: 2013-07-01 ถึง 07-05 และ 2013-10-18 ถึง 10-21 ทั้งวันเกือบไม่มีทริป วันที่ขาด 2013-10-19/20 ในข้อ 2 ก็อยู่ในช่วง strike นี้
9. **วันที่ข้อมูลไม่ครบบางชั่วโมง (partial)**: 2011-10-14 (หายตั้งแต่ 9 โมง), 2011-10-16 และ 2019-03-09 (หายช่วง 7–8 โมง)
10. **วันหยุด**: ใช้วันหยุดราชการ US ยกเว้น Columbus Day, Veterans Day และ Juneteenth (ผู้โดยสาร ~75–100% ของวันปกติ) และเพิ่ม Day after Thanksgiving (~50%)
11. **ทริปหลงก่อนวันเปิดสถานี** 462 แถว / 1,253 ทริป ตัดออกจาก marts (fact table ยังเก็บไว้)

### กฎการเติมข้อมูลและใช้ข้อมูล (ตั้งแต่ notebook 02 เป็นต้นไป)
- marts เติมให้ครบตามเวลา: ชั่วโมงที่ไม่มีแถวใส่ 0, วัน `no_data` ใส่ค่าว่าง (NULL) ห้ามใส่ 0, ก่อนวันเปิดสถานีไม่สร้างแถว
- `calendar.day_status` มี 4 ค่า: `normal`, `no_data`, `strike`, `partial`
- กราฟ ค่าเฉลี่ย และ target/lag ของโมเดลใช้เฉพาะวัน `normal` (M3 ใช้วัน strike เป็นตัวอย่างตรวจจับเหตุการณ์)
- กราฟและค่าเฉลี่ยอ่านจาก marts ไม่อ่าน fact table ตรงๆ ยกเว้นงานที่ต้องใช้ OD รายชั่วโมง (เช่น Q3) ให้เติมศูนย์เฉพาะช่วงที่ใช้
- exits ใช้ชั่วโมงเดียวกับในข้อมูล เพราะ feed มีชั่วโมงเดียวต่อทริป

## 3. เครื่องมือและเหตุผลที่เลือก

อ้างอิงสเปกเครื่องจาก [`machine_spec.md`](machine_spec.md): i9-13900H (20 เธรด), RAM 32 GB DDR5-5200, RTX 4060 Laptop 8 GB, NVMe ที่เข้ารหัส LUKS

| เครื่องมือ | ใช้ทำอะไร | เหตุผลที่ผูกกับเครื่องนี้ |
|---|---|---|
| **uv + Python 3.12** | จัดการ environment | Python 3.14 ของระบบยังไม่มี wheel GPU บางตัว ส่วน 3.12 เสถียร |
| **DuckDB** | ingest CSV → Parquet และ SQL aggregation หนักๆ | vectorized + ใช้ได้ทุกเธรด, ตั้ง `memory_limit` ให้ spill ลง NVMe ได้ |
| **Parquet (zstd)** | storage หลัก | ลด I/O บนดิสก์ที่เข้ารหัสและเป็นแบบ DRAM-less, อ่านเฉพาะคอลัมน์ที่ใช้, ข้ามข้อมูลได้ด้วย row-group statistics |
| **Polars (lazy)** | feature engineering, reshape | query optimizer + streaming, ทำ window function ได้เร็ว |
| **PyArrow** | ตัวกลางส่งข้อมูลแบบ zero-copy ระหว่าง DuckDB, Polars และ pandas/XGBoost | ไม่ต้อง copy ข้อมูลซ้ำใน RAM |
| **psutil** | จับเวลา, peak RAM, CPU% ของแต่ละขั้นตอน | เก็บหลักฐานการใช้ทรัพยากรไว้แสดงใน notebook สรุป |
| **XGBoost (CUDA)** | M1, M3 | งานที่ข้อมูลหลายล้านแถวและต้องจูนหลายรอบ ใช้ GPU คุ้ม |
| **scikit-learn** | M2 | ข้อมูลเล็ก (~100 ตัวอย่าง) ใช้ CPU เหมาะกว่า เพราะ GPU จะมีแต่ overhead |
| **Optuna** | จูน hyper-parameter ของ M1 | |
| **SHAP** | อธิบายโมเดล M1 | ใช้ TreeSHAP บน GPU ผ่าน XGBoost |
| **Plotly** (+ kaleido) | กราฟทั้งหมด ใช้ template `bart_clean` ใน `src/bart/viz.py` (พื้นสว่าง สะอาด, หัวกราฟบอก insight) | interactive ใน notebook (hover/zoom) และเซฟเป็น `.html` + `.png` ใน `outputs/figures/`; kaleido ใช้ Google Chrome ที่มีในเครื่อง |
| matplotlib | เฉพาะกราฟที่ SHAP สร้างเอง (ถ้าจำเป็น) | |

**หลักการเลือกอุปกรณ์:** เลือกตามขนาดและลักษณะงาน งานใหญ่และขนานได้ใช้ GPU งานเล็กใช้ CPU และเขียนเหตุผลกำกับไว้ใน notebook ทุกครั้ง
**ไม่ทำ benchmark เทียบเครื่องมือ** ใช้วิธีที่ดีที่สุดไปเลย แต่จะบันทึกเวลาและทรัพยากรที่ใช้ของแต่ละขั้นด้วย psutil

### การตั้งค่าเครื่องที่ต้องคุมทุกครั้งที่รัน
- เสียบสายชาร์จ, platform profile = `performance`
- DuckDB: `threads=20`, `memory_limit≈20GB`, กำหนด `temp_directory`, `preserve_insertion_order=false` (ยกเว้นตอนเขียน Parquet ที่ต้องเรียง ให้เปิดเป็น true ชั่วคราว และเขียนทีละปีเองแทน `PARTITION_BY` เพราะ `PARTITION_BY` ไม่รักษาลำดับ)

## 5. EDA (สำคัญมาก — ทำก่อนตอบคำถามธุรกิจและก่อนทำโมเดล)

notebook: `03_eda.ipynb` ใช้ข้อมูลจาก `data/marts/` (และ fact table สำหรับ OD)

เป้าหมาย: เข้าใจข้อมูลก่อนตั้งสมมติฐาน ใช้ผลของ EDA เป็นเหตุผลรองรับ Q1–Q4 และการออกแบบ feature ของ M1 ทุกหัวข้อต้องจบด้วยข้อสังเกตสั้นๆ ว่าเห็นอะไร และเอาไปใช้ต่อที่ไหน

วิธีทำ: notebook เดียว สร้างทีละส่วน (ส่วนละ 1 หัวข้อ) ทดสอบแล้วให้ผู้ใช้รัน ดูผล เขียนข้อสังเกต แล้วค่อยขออนุมัติส่วนถัดไป ใช้เฉพาะวัน `normal` เทียบก่อน/หลังด้วย ม.ค.–เม.ย. 2019 vs ม.ค.–เม.ย. 2023 (ช่วงเดียวกับ Q1–Q4)

### 5.1 ภาพรวมและการกระจาย
- ตารางภาพรวมรายปี: จำนวนแถว, ทริป, คู่ OD ที่มีการเดินทางจริงเทียบกับที่เป็นไปได้
- ความเบาบาง: สัดส่วนแถว OD-ชั่วโมงที่มี 1–2 ทริป, percentile ของ trips, histogram บน log scale (สัดส่วนแถว vs สัดส่วนทริป)
- entries ต่อสถานี-ชั่วโมง: สัดส่วนศูนย์ (ช่วงมีรถวิ่ง vs ตี 1–4), histogram 2019 vs 2023
- mean vs variance ของ entries (overdispersion) และประมาณ Tweedie power จาก var ∝ mean^p → เลือก objective ของ M1 และเหตุผลที่ใช้ WAPE แทน MAPE

### 5.2 รูปแบบตามเวลา
- trend รายเดือน (ค่าเฉลี่ยต่อวันทำงาน) 2011–2023 พร้อมเส้นแบ่งช่วง COVID
- profile รายชั่วโมง วันทำงาน vs เสาร์-อาทิตย์ (double peak) 2019 vs 2023
- heatmap วันในสัปดาห์ × ชั่วโมง ก่อน/หลัง COVID (สัดส่วน)
- ฤดูกาลรายเดือน (index ปี 2012–2019) และผลของวันหยุด
- วันพีคผิดปกติ (เช่น 2012-10-31) ตรงกับเหตุการณ์อะไร → ตัวอย่างสำหรับ M3

### 5.3 สถานี
- อันดับสถานีและสัดส่วนสะสม (top 10) 2019 vs 2023
- ขาเข้า vs ขาออกช่วงเช้า (6–9) แยกสถานีที่พักกับที่ทำงาน
- profile รายชั่วโมงของสถานีตัวอย่าง (MONT, DUBL, SFIA, 16TH) → ที่มาของ M2

### 5.4 Origin-Destination
- OD matrix heatmap เรียงตาม corridor ก่อน/หลัง COVID
- ความเข้มข้นของ flow: คู่ OD กี่ % ที่รวมกันได้ 50% / 80% ของทริป
- สัดส่วนทริปข้าม Transbay Tube รายปี → ที่มาของ Q3

### 5.5 ความสัมพันธ์ตามเวลา (สำหรับ M1)
- autocorrelation ของ system_hour lag 1–336 ชม. (ปี 2019)
- correlation ของ entries สถานี-ชั่วโมงกับค่าเมื่อ 1, 2, 3, 4, 52 สัปดาห์ก่อน
- WAPE ของ baseline "สัปดาห์ก่อน" และ "ค่าเฉลี่ย 4 สัปดาห์" ในช่วง valid ของ M1 (ก.ค.–ธ.ค. 2022) = เป้าที่ M1 ต้องชนะ (ไม่แตะช่วง test)

### 5.6 สรุป EDA
- รายการข้อค้นพบสั้นๆ และบอกว่าแต่ละข้อนำไปใช้ใน Q ไหน หรือโมเดลไหน

## 6. คำถามธุรกิจ

ช่วงเปรียบเทียบหลัก "ก่อน vs หลัง": **ม.ค.–เม.ย. 2019 vs ม.ค.–เม.ย. 2023** (เดือนเดียวกันเพื่อตัดผลของฤดูกาล และเป็นเดือนที่ครบที่สุดของปี 2023) ใช้เฉพาะวันทำงาน และตัดวันหยุดราชการ US ออก ยกเว้นข้อที่ระบุเป็นอย่างอื่น

### Q1 — ผู้โดยสารฟื้นตัวหลัง COVID แค่ไหน และช่องว่างอยู่ที่ไหน
- **Pain point:** รายได้ค่าโดยสารหายไป แต่ต้นทุนการเดินรถยังเท่าเดิม ไม่รู้ว่าควรคงหรือลดบริการตรงไหน
- **วิเคราะห์:**
  - trend ผู้โดยสารเฉลี่ยวันทำงานรายเดือน 2011–2023 พร้อม recovery index เทียบเดือนเดียวกันของปี 2019
  - การฟื้นตัวแยกตามวันในสัปดาห์ (ดูผลของ hybrid work: อ.–พฤ. เทียบ จ./ศ. และเทียบเสาร์-อาทิตย์)
  - การฟื้นตัวแยกตามสถานีและ corridor และสัดส่วนผู้โดยสารที่หายไปของแต่ละ corridor
- **ตัวชี้วัด:** recovery % = ค่าเฉลี่ยปี 2023 / ค่าเฉลี่ยปี 2019
- **ตรวจซ้ำ (notebook 13):** recovery % เทียบกับ counterfactual = ค่าจริง / ค่าที่ SARIMA (เทรนเฉพาะก่อน COVID) คาดว่าจะเป็นถ้าไม่มี COVID
- **การตัดสินใจที่ได้:** จัดสรรความถี่ตามวันในสัปดาห์และ corridor, ทำการตลาดเจาะกลุ่มที่ฟื้นช้า

### Q2 — รูปทรงของ peak hour เปลี่ยนไปไหม
- **Pain point:** ตารางเดินรถออกแบบไว้สำหรับ peak ก่อน COVID ถ้า peak เปลี่ยนรูป จะมีรถเกินในบางชั่วโมงและแน่นในบางชั่วโมง
- **วิเคราะห์:**
  - profile ผู้โดยสารรายชั่วโมงของวันทำงาน ทั้งค่าจริงและสัดส่วน (normalize เพื่อดูเฉพาะรูปทรง) 2019 vs 2023
  - peak-to-average ratio และสัดส่วนของช่วง AM (6–9) / PM (15–18)
  - heatmap การฟื้นตัวรายสถานี × ชั่วโมง
- **การตัดสินใจที่ได้:** ปรับ headway ของแต่ละช่วงเวลา, หาช่วงที่ลดความถี่ได้หรือต้องเพิ่ม

### Q3 — โหลดกระจุกที่ไหน
- **Pain point:** Transbay Tube คือคอขวดด้านความจุของทั้งระบบ ต้องรู้ว่าทิศไหนและชั่วโมงไหนที่กำหนดจำนวนตู้ที่ต้องใช้
- **วิเคราะห์:**
  - จำนวนทริปที่ข้าม Transbay Tube (ต้นทางกับปลายทางอยู่คนละฝั่งอ่าว) รายชั่วโมงและแยกทิศ 2019 vs 2023
  - สัดส่วนทริปที่ข้าม Tube ต่อทริปทั้งหมด
  - คู่ OD ที่หนาแน่นที่สุด (top 20) และการฟื้นตัวของแต่ละคู่
  - ความไม่สมดุลระหว่างขาเข้า/ขาออกในช่วงเช้าของแต่ละสถานี
- **การตัดสินใจที่ได้:** ความยาวขบวนต่อช่วงเวลาและทิศทาง, การวางขบวนเปล่าตอนกลับทิศ

### Q4 — สถานีใหม่สร้างผู้โดยสารใหม่ หรือแค่ย้ายมาจากสถานีเดิม
- **Pain point:** การขยายเส้นทางใช้งบหลายพันล้าน ต้องรู้ว่าได้ผู้โดยสารใหม่จริงเท่าไร
- **วิเคราะห์:**
  - **eBART (ANTC + PCTR, เปิด 2018-05-26):** เป็นกรณีทดสอบที่สะอาด เพราะเกิดก่อน COVID เทียบสถานีข้างเคียง (PITT, NCON, CONC) 12 เดือนก่อนกับ 12 เดือนหลังเปิด และคำนวณ net gain ของทั้ง corridor
  - **Warm Springs (WARM, เปิด 2017-03-25):** กรณีสะอาดที่สองก่อน COVID เทียบกับ FRMT, UCTY, SHAY แบบเดียวกับ eBART
  - วิธีวัด: ผู้โดยสารใหม่สุทธิ = entries ของกลุ่มหลังเปิด - entries ก่อนเปิด × การเปลี่ยนแปลงของส่วนที่เหลือของระบบ และทดสอบด้วยกลุ่มสถานีที่กว้างขึ้น
  - **Silicon Valley (MLPT + BERY, เปิด 2020-06-13):** เปิดตรงกับช่วง COVID จึงทำได้แค่ดูสัดส่วนเทียบกับ WARM/FRMT และ**ต้องระบุข้อจำกัดให้ชัด**
- **การตัดสินใจที่ได้:** ใช้เป็นบทเรียนสำหรับโครงการขยายเส้นทางในอนาคต เช่น เรื่องที่จอดรถและ feeder bus

## 7. โมเดล ML

### M1 (ตัวหลัก) — พยากรณ์ผู้โดยสารเข้าสถานีรายชั่วโมงล่วงหน้า 7 วัน
- **การใช้งานทางธุรกิจ:** ทุกสัปดาห์ฝ่ายวางแผนต้องกำหนดความยาวขบวน ความถี่ และพนักงานของสัปดาห์หน้า
  - **P50** = แผนหลัก
  - **P90** = ขบวน/ตู้สำรองสำหรับกรณีความต้องการสูง
  - **P10** = ช่วงที่ลดความถี่ได้อย่างปลอดภัย
- **ข้อมูล:** ตารางสถานี × วันที่ × ชั่วโมง ที่เติมศูนย์แล้ว (~5 ล้านแถว), target = entries
- **Features** (ทุก lag ต้อง ≥ 168 ชม. เพื่อกัน leakage):
  - ค่า same-hour ย้อนหลัง 1, 2, 3, 4 และ 52 สัปดาห์ พร้อม mean/median/std ของ 4 สัปดาห์
  - ระดับผู้โดยสารของสถานีในช่วง 7 และ 28 วัน (นับถอยจาก 7 วันก่อน) และ trend
  - lag ระดับทั้งเครือข่าย
  - ปฏิทิน: ชั่วโมง, วันในสัปดาห์, เดือน, วันหยุด US, จำนวนวันก่อน/หลังวันหยุด
  - ช่วง COVID, จำนวนวันที่สถานีเปิดมาแล้ว, รหัสสถานี (categorical)
- **ตรวจ leakage:** สุ่มแถวมาตรวจว่าค่า lag ตรงกับค่าจริงของวันที่ย้อนหลัง
- **แบ่งข้อมูลตามเวลา:**
  - train: 2011-01 → 2022-06 (ตัดช่วง break 2020-03-09 → 2020-05-31)
  - valid: 2022-07 → 2022-12 (ใช้จูนและ early stopping)
  - test: 2023-01 → 2023-05-02 (ใช้ครั้งเดียวตอนจบ)
- **โมเดล:** XGBoost `device="cuda"`, objective Tweedie (เหมาะกับข้อมูลนับที่มีศูนย์เยอะ), ใช้ `QuantileDMatrix`
  - โมเดล quantile แยก (pinball loss) สำหรับ P10/P50/P90
- **จูน:** Optuna (TPE) ค้นหาทั้งปีเริ่มต้นของข้อมูล train และ recency weight ด้วย
  - เริ่มจาก trial น้อยเพื่อทดสอบก่อน แล้วค่อยรันเต็ม (จำนวน trial ต้องขออนุมัติ)
  - ใช้ `python -u` และ log ความคืบหน้าราย trial
- **ตัวชี้วัด:** WAPE (ตัวหลัก), MAE, RMSE, R², coverage ของช่วง P10–P90 (เป้าคือ ~80%)
  - แยกผลตาม segment: ทั้งหมด, AM peak, PM peak, เสาร์-อาทิตย์, วันหยุด, และระดับสถานี-วัน
- **Baseline ที่ต้องชนะ:** ค่าของชั่วโมงเดียวกันเมื่อสัปดาห์ก่อน และค่าเฉลี่ยของ 4 สัปดาห์
- **อธิบายผล:** SHAP importance

### M2 — จัดกลุ่มสถานีตามบทบาท (2019 vs 2023)
- **การใช้งานทางธุรกิจ:** วางตารางเดินรถและพนักงานตามประเภทของสถานี และดูว่าสถานีไหนเปลี่ยนบทบาทหลัง COVID
- **Features:** สัดส่วนผู้โดยสารเข้าและออกรายชั่วโมงของวันทำงาน (ใช้ 20 + 20 ค่า คือ 5:00-0:00 เพราะตี 1-4 แทบไม่มีผู้โดยสาร ถ้าใส่ StandardScaler จะขยาย noise) และอัตราส่วนวันหยุด/เสาร์-อาทิตย์ต่อวันทำงาน รวม 41 ค่า
- **วิธี:** StandardScaler → KMeans โดย fit ปี 2019 และ 2023 รวมกัน เพื่อให้ cluster มีความหมายเดียวกันทั้งสองปี
  - เลือก k จาก silhouette ร่วมกับความเสถียร (ARI ข้าม 50 seed)
  - ตั้งชื่อ cluster จาก centroid
- **ผลลัพธ์:** profile ของแต่ละกลุ่ม, PCA map, ตารางสถานีที่เปลี่ยนกลุ่ม

### M3 — Backtest + ตรวจจับเหตุการณ์
- **(ก) Rolling-origin backtest:** เทรน M1 ใหม่ทุก quarter ด้วยข้อมูลก่อนหน้า แล้วพยากรณ์ quarter ถัดไป ตั้งแต่ 2021-Q3 ถึง 2023-Q2 เพื่อพิสูจน์ว่าความแม่นยำคงที่ ไม่ได้ฟลุคจาก test ช่วงเดียว
- **(ข) Event detection:** ใช้ residual ที่หลุดนอกช่วง P10–P90 (ทั้งหมดเป็น out-of-sample)
  - **Surge** (ค่าจริงสูงกว่า P90 มาก) = งานอีเวนต์ที่ต้องเพิ่มรถหรือพนักงาน
  - **Drop** (ค่าจริงต่ำกว่า P10 มาก) = ระบบขัดข้องหรือเหตุการณ์ผิดปกติ
- **ผลลัพธ์:** error ราย quarter, รายการวันที่มีเหตุการณ์, สถานีที่มีอีเวนต์บ่อย

## 9. ความเสี่ยงและวิธีรับมือ

| ความเสี่ยง | วิธีรับมือ |
|---|---|
| งานบน GPU ใช้เวลานานจนมองไม่เห็นความคืบหน้า | เริ่มจาก trial น้อย, log ทุก trial, แจ้งเวลาโดยประมาณก่อนรัน |
| VRAM 8 GB ไม่พอ | ใช้ `QuantileDMatrix`, ใช้ float32, ตรวจ VRAM ก่อนรัน |
| Data leakage ใน M1 | กำหนดทุก lag ≥ 168 ชม., ตรวจด้วยตัวอย่างจริง, แบ่งข้อมูลตามเวลา |
| ผลจาก COVID ทำให้ข้อสรุปเพี้ยน | เทียบเดือนเดียวกัน, ตัดช่วง break ออกจาก train, ระบุข้อจำกัดให้ชัด |
| ข้อสรุปของ Q4 (Silicon Valley) ถูก confound | ระบุข้อจำกัด, ใช้กรณี eBART เป็นหลักฐานหลัก |
